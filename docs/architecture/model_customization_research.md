# Model Customization — What's Actually Possible, For Each Version

Research note answering the question "which customization techniques can we actually run, on what model, on which cloud?" Sources: AWS Bedrock custom-model-fine-tuning docs, Bedrock Model Distillation docs, Bedrock OpenAI-compatible fine-tuning docs, Qwen model card on Bedrock, Alibaba PAI and Model Studio docs, Hugging Face TRL + SageMaker tutorials, plus the linked AWS builder article on GRPO for tool-calling.

## 1. The five techniques — plain definitions

| Technique | Goal | Input data | Output |
|---|---|---|---|
| **SFT** (supervised fine-tuning) | Teach the model to imitate good answers on a specific task | `(prompt → target_answer)` pairs | Updated weights |
| **DPO** (direct preference optimization) | Teach the model that one answer is preferred over another | `(prompt, chosen_answer, rejected_answer)` triples | Updated weights |
| **RLHF** | DPO's ancestor; train a reward model then do RL against it | Human preference labels + RL infra | Updated weights |
| **Knowledge distillation** | Transfer a big model's behavior into a smaller, faster one | Big teacher + small student + prompts | SFT (or sometimes DPO) dataset generated by the teacher + a fine-tuned student |
| **GRPO / Reinforcement fine-tuning** | RL against a verifiable reward (e.g., "did the answer match the ICD-11 code?"); no separate reward model | Prompts + a grader / reward function | Updated weights |

**Distillation is not a fourth technique.** It's a way to *generate the training data* for SFT/DPO without paying human labelers — a big teacher writes the answers a clinician would otherwise have to write.

## 2. What Nova actually needs (scenario-driven)

| Scenario need | Best technique |
|---|---|
| "Answer complex medical questions in natural language" | Base capability of any foundation model + RAG. No fine-tune needed. |
| "Rely on internal trial reports + WHO + ICD-11" | RAG. Fine-tune can't replace it because WHO updates monthly. |
| "Consistent tone and phrasing" | **SFT** on Nova-approved answers; **DPO** if we have "the old tool's answer vs the new preferred answer" pairs. |
| "Emergency 2-second SLA" | Smaller, faster model. A distilled student (teacher = Sonnet / Qwen-Max, student = Haiku-class / Qwen3-8B) with **SFT** as the training method. |
| "Patient-sensitive data in internal trials" | Never put PHI in training data. De-identify first. Applies to all three techniques. |

## 3. Per-cloud reality — what is fine-tunable today

### AWS Bedrock — custom fine-tuning (from the AWS doc)

| Provider | Model | Fine-tuning region |
|---|---|---|
| Amazon | Nova 2 Lite / Nova Lite / Nova Micro / Nova Pro / Nova Canvas | us-east-1 |
| Amazon | Titan Image Generator G1 v2 / Titan Multimodal Embeddings | us-east-1, us-west-2 |
| **Anthropic** | **Claude 3 Haiku (2024-03-07 v1)** | **us-west-2 only** |
| Meta | Llama 3.1 8B / 70B, Llama 3.2 1B / 3B / 11B / 90B, Llama 3.3 70B | us-west-2 |

**Key constraints the user flagged:**

- Only **Claude 3 Haiku** is fine-tunable on Bedrock. **Not** Haiku 4.5, 4, 3.5 — just the 2024-03-07 snapshot.
- Claude 3 Haiku hyperparameters: `epochCount 1–10 (default 2)`, `batchSize 4–256 (default 32)`, `learningRateMultiplier 0.1–2 (default 1)`, `earlyStoppingThreshold 0–0.1 (default 0.001)`, `earlyStoppingPatience 1–10 (default 2)`.
- Claude 3 Haiku fine-tuning is **SFT only**. No DPO, no RLHF on Bedrock for Claude.

### AWS Bedrock — Model Distillation (managed, end-to-end)

- Automates the whole distillation flow: give it prompts → it asks the teacher → it trains the student → you get a custom student endpoint.
- Two data sources allowed: prompts you provide, or invocation logs from your production traffic (recommended for clinical — clinician questions become the seed set).
- You can supply "golden examples" as prompt-response pairs to steer the teacher's generations.
- Uses the teacher's on-demand price to generate the SFT dataset; charges you for the teacher inference plus the fine-tuning job.
- Available teacher/student pairs include Nova Premier → Nova Pro/Lite/Micro; Llama 3.1 70B → Llama 3.1 8B, etc. Confirm the current pairs list before committing.

### AWS Bedrock — OpenAI-compatible fine-tuning (open-weight models, reinforcement fine-tuning)

This is the new `bedrock-mantle` endpoint. Two models on the list as of the AWS doc:

- **OpenAI gpt-oss-20B** (`openai.gpt-oss-20b`), us-west-2.
- **Qwen3 32B** (`qwen.qwen3-32b`), us-west-2.

- Fine-tuning style: **reinforcement fine-tuning with a reward function** (Lambda-defined grader). Closest to GRPO in spirit.
- You also get intermediate checkpoints, Files API to upload JSONL, and the OpenAI SDK shape.
- This is the path for "run Qwen on AWS with real fine-tuning".

### AWS Bedrock — hosted Qwen models (inference only)

- `qwen.qwen3-vl-235b-a22b` is available on `bedrock-runtime` and `bedrock-mantle` endpoints for **inference only** — no managed fine-tuning.
- Combined with `qwen.qwen3-32b` fine-tuning above, that gives a fully-Qwen path on AWS.

### SageMaker path (all open weights, all techniques)

Outside Bedrock, SageMaker lets us run essentially anything with Hugging Face TRL:

- **SFT** on Qwen3-8B / Qwen3-32B / any HF open-weight.
- **DPO** with TRL's DPO trainer.
- **GRPO** via TRL's GRPOTrainer (the AWS builder article on tool-calling with GRPO uses exactly this).
- Serve on SageMaker endpoints (A10 / A100 / L40) or drop into PAI-EAS for the Alibaba side.

This is where real, flexible fine-tuning lives on AWS. Bedrock is simpler; SageMaker is more capable.

### Alibaba Cloud PAI — Qwen open weights

From `askAli_AI_Assistant.txt` and current Alibaba docs:

| Model | Supported techniques on PAI |
|---|---|
| Qwen3 0.6B / 1.7B / 4B / 8B / 14B / 32B | SFT (full / LoRA / QLoRA), **DPO**, **GRPO** |
| Qwen2.5 (7B-Instruct, 32B-Coder, etc.) | SFT + DPO |
| Qwen1.5 Base / Chat | SFT + DPO |
| Qwen-7B-Chat | LoRA via Arena CLI on ACK |

Plus Model Studio's HTTP API offers token-billed fine-tuning for Qwen-Plus / Qwen-Turbo variants without exposing weights — click-and-train.

## 4. What this means for Nova — corrected plan per version

### Version A — AWS with Claude (running demo, verified)

- **Base**: Claude Haiku 4.5 (emergency) + Claude Sonnet 4.5 (complex) via Bedrock Converse.
- **Fine-tuning of Haiku 4.5 is NOT possible.** Anthropic does not expose 4.5 weights for SFT on Bedrock.
- Two realistic customization paths:
  1. **Fine-tune Claude 3 Haiku (the 2024-03-07 snapshot)** via Bedrock custom models on `us-west-2`. This is SFT-only. The trade-off: we give up Haiku 4.5's quality gains to unlock custom training. Not worth it unless the quality loss from 3 → 4.5 is smaller than the gain from fine-tuning for tone.
  2. **Keep Claude 4.5 base + use Bedrock Model Distillation** from Sonnet → **Nova Lite / Nova Micro** as the "student". You lose Claude branding in the fast lane but gain a genuinely smaller, tunable model. **This is the launch default for Version A** — the student is trained before cut-over and serves 100% of the fast lane on day one.
- For the 2-second SLA, Bedrock Prompt Caching + semantic cache + the right region keep even base Haiku 4.5 under 2s **without** fine-tuning. Fine-tuning layers on tone consistency and cost reduction, not raw latency.
- **Status**: the running demo is plain RAG (no training yet). The production launch builds a trained student before cut-over; the demo stays as a baseline comparator.

### Version B — AWS with Qwen (new, simplified)

- **Base models on Bedrock Sydney (no SageMaker needed for serving):**
  - Fast lane: **Qwen3 Next 80B A3B** via `qwen.qwen3-next-80b-a3b` — MoE with 3B active per token, `$0.1545 in / $1.2360 out` per 1M.
  - Complex lane: **Qwen3 VL 235B A22B** via `qwen.qwen3-vl-235b-a22b` — vision-enabled, 22B active, `$0.5459 / $2.7398`. Split to Qwen3 235B text-only (`$0.2266 / $0.9064`) for non-figure queries.
- **Customization (when needed):**
  - **Path B-1 — Bedrock Reinforcement Fine-Tuning on Qwen3 32B** (us-west-2 only). $80/hr training, then $0.20/$0.78 per 1M on custom-model inference. Fully managed — no GPU cluster to run.
  - **Path B-2 — SageMaker + TRL GRPO on Qwen3-1.7B/4B** (AWS builder article). Runs `ml.g6e.8xlarge` in SG, serves from SageMaker SG endpoint. Use when the student must physically live in Singapore for PDPA.
- Vector store: OpenSearch Serverless (same as Version A).
- Embeddings: Cohere Embed v4 on Bedrock.
- Serving region: Sydney for Bedrock Qwen; Singapore for all other AWS services; us-west-2 only during the Bedrock RFT training job.

### Version C — Alibaba Cloud (Qwen, Singapore)

- **Base**: Qwen3.5-Flash (fast) + Qwen3.5-Plus (complex, teacher — Feb 2026 release; replaced the older Qwen-Max) on Model Studio in the Singapore region. Embeddings: `text-embedding-v4` + `tongyi-embedding-vision-plus`. Reranker: `qwen3-rerank`. See `docs/architecture/regional_availability.md` §8 for SG International availability.
- **Student**: Qwen3-8B fine-tuned on PAI Model Gallery with **SFT + LoRA**, optionally + DPO. GRPO available for a future round if we need reasoning/verifiable-reward alignment.
- The entire chain — inference, fine-tune, serve — is native Alibaba, single-vendor, Singapore-resident.
- Cheapest of the three. Most flexible for fine-tuning technique. Biggest question mark is the regulatory posture for US-onboarded hospitals.

## 5. Honest status of the running AWS demo

- Deployed to `http://13.213.123.169/` (Singapore EC2 t4g.small).
- Uses **plain Claude Haiku 4.5 and Sonnet 4.5 from Bedrock**. No fine-tuning whatsoever.
- FAISS in-memory index built from the real corpus (WHO COVID guideline + internal Chapter 1 PDF + ICD-11 entities).
- LangChain + LangGraph. Explicit emergency toggle in the UI routes via if/else to Haiku or Sonnet.
- Next step (not yet done): RAG quality + latency measurements on this deployment, before deciding which customization path to invest in.

## 6. Next decisions to make (ordered)

1. **Measure** the RAG response time on the running demo across 30–50 clinical questions, warm and cold cache. If p95 is already under 2s on the emergency lane with just Haiku 4.5 + RAG + caching, fine-tuning is quality-only, not latency. (User explicitly asked for this in a new isolated AWS-with-Claude environment — see §7.)
2. **Pick the Claude-version customization path** once we have the latency numbers:
   - If the 2s budget is comfortable → distill Sonnet → **Nova Lite** as the launch-day student, keeping Haiku 4.5 as the unmodified same-API fallback.
   - If we need more control over Haiku specifically → fall back to Claude 3 Haiku SFT on us-west-2, accepting the older model trade-off.
3. **Compare against the Qwen paths** on the same benchmark (same questions, same corpus): cost-per-call, p95 latency, and answer quality as judged by an LLM-as-judge harness. Pick the winner per client segment (US-client default = Version A; international = Version A or C; cost-sensitive = C).
4. Only then **commit to a fine-tuning run** and implement the teacher-dataset pipeline.
